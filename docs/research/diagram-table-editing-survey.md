# 격자형 네이티브 레이아웃이 다이어그램·정의서 공백을 메운다

2026년 10월 현재 Gamma·Canva·Manus·Presentations.AI·PowerPoint Copilot·Google Slides·Figma Slides 가운데 UML 계열(시퀀스·클래스·상태·유스케이스 등)을 **슬라이드 안에서 네이티브 객체로 만들어 주는 제품은 하나도 없다**. 슬라이드 제품이 자체 지원하는 범위는 플로차트(도형+커넥터)·SmartArt 류 프로세스/계층 인포그래픽·타임라인까지이고, UML·ERD 를 텍스트에서 편집 가능 객체로 얻는 가장 짧은 경로는 FigJam(Mermaid 붙이기·MCP)이며, PPTX 로는 mmd2pptx·diagram-pptx 같은 0.x 변환기가 플로차트 중심으로만 있다. nexa-slide 는 이미 `rect/pill/ellipse/text` 와 `line/arrow/curve` 요소, 편집기의 화살표 끝점 드래그, PPTX 커넥터+화살 머리 XML, 그리고 네이티브 `sequence`·`flow`·`tree` 레이아웃을 갖고 있어 **부족한 것은 "노드·엣지 → 좌표" 를 만드는 생성 쪽뿐**이다. 그래서 권고는 Mermaid 이미지 경로(접근 1)를 버전 고정 뒤 폴백으로 유지하면서 **격자 지정형 네이티브 구조 레이아웃(접근 3)** 을 기본으로 삼고, 공통 기반(도형 변형·연결 유틸·`stCxn/endCxn`·parity 검사 확장)을 먼저 깐 뒤 flowchart·ERD·state·DFD 부터 넣는 것이다. 테이블 정의서는 요소 `table` 을 재사용하는 `table_spec` 레이아웃으로 **7열(순번·컬럼명·설명·타입·PK·NULL 허용·기본값)·본문 8~9행·머리 행 반복 분할**(TB_BOM 23컬럼 = 8·8·7 세 장) 하고, 입력은 `schema/<프로파일>/snapshot/columns.csv` 또는 딕셔너리 SQL 에서 스크립트가 만든다. 편집 기능은 15개 후보 중 요청 칩 확장·노트 생성 칩·입력 중 길이 경고·다중 선택 정렬·덱 찾기/바꾸기·내용 유지 유형 전환 6개가 S~M 로 바로 효과를 내며, 테마 전환·브랜드 킷·AutoFit·분석·댓글은 "기능만 차용, 구성·디자인 유지" 원칙에 따라 제외한다.

## 슬라이드 제품은 2026년에도 UML 을 네이티브로 그리지 않는다

열두 제품을 열세 가지 다이어그램 계열로 교차해 보면 결론은 한 줄이다. **UML 메타모델(생명선·메시지·상태 전이 같은 의미 객체)을 가진 슬라이드 제품은 없고**, "지원" 이라 불리는 것은 (a) 범용 도형+커넥터로 손으로 그리기 아니면 (b) 외부 다이어그램 도구의 이미지 임베드 둘 중 하나다. Gamma 의 Smart Diagrams(2025-09 베타)는 Insert 메뉴나 `/diagram` 으로 넣는 빈 캔버스에 도형·선·화살표를 추가하는 수준이고 ([Gamma Help](https://help.gamma.app/en/articles/11029098-how-can-i-generate-charts-and-diagrams-in-gamma)), 그 유형은 Venn·Iceberg·Quadrant·Road 같은 인포그래픽 12종 이상이다 (2차, [Lead with AI](https://www.leadwithai.co/article/build-impactful-decks-with-gammas-smart-diagrams)). 사용자들이 플로차트·스윔레인·Gantt 를 요청하자 Gamma 디자이너는 Gantt 를 "리소스 제약, on our radar" 라 답했고, 의사결정 트리 변환이 4단계까지만 읽힌다는 보고도 있다 ([Gamma Ideas](https://ideas.gamma.app/ideas/p/more-charts-and-diagrams-swim-lane-diagrams-gantt-charts-org-charts-etc)). Canva 는 선을 도형 테두리에 붙이면 도형을 옮겨도 따라가는 스마트 커넥터와 Quick Flow, "UML 다이어그램을 Canva Whiteboard 에서 만들기" 도움말, DFD 전용 템플릿 페이지까지 있어 "템플릿+수동" 범위가 가장 넓지만 ([Canva Help: connect lines](https://www.canva.com/en_gb/help/connect-lines-to-elements/), [Canva Help: UML](https://www.canva.com/help/create-uml-diagrams-canva-whiteboards/), [Canva DFD](https://www.canva.com/graphs/data-flow-diagrams/)), "Mermaid diagram" 페이지는 구문 입력 기능이 아니라 "구문 없이 만든다" 는 마케팅 랜딩이다 (검색 요약 기준, [Canva](https://www.canva.com/graphs/mermaid-diagram/)). Manus 의 AI Flowchart Generator 는 프로세스·의사결정 트리·스윔레인·사용자 여정·시스템 아키텍처를 자연어로 생성하되 산출물은 Mermaid·SVG·PNG·PDF 이고 PPTX 직접 내보내기 언급이 없다 ([Manus](https://manus.im/tools/ai-flowchart-generator)). Presentations.AI 공식 사이트에는 다이어그램 기능 서술 자체가 없다 ([Presentations.AI](https://www.presentations.ai/)).

PowerPoint 는 SmartArt Process 와 도형 커넥터(연결점에 붙어 따라감)로 플로차트를 그리고 Copilot 이 "리스트를 SmartArt 타임라인으로" 같은 프롬프트를 처리하지만, 플로차트·UML 생성은 공식 문서에 없고 커뮤니티에서는 Designer 가 "너무 창의적인" 그림을 만든다는 보고가 있다 ([MS Support: Edit with Copilot](https://support.microsoft.com/en-us/powerpoint/edit-with-copilot-in-powerpoint), [Tech Community](https://techcommunity.microsoft.com/discussions/copilotforsmallandmediumbusiness/copilot-for-smartart-in-powerpoint/4166198)). Visio Data Visualizer 는 Excel 전용이며 **2026년 3월 은퇴**가 명시됐다 ([MS Support](https://support.microsoft.com/en-us/office/create-a-diagram-in-excel-with-the-visio-data-visualizer-add-in-bee3b5aa-aaaf-4401-acc6-276b711c763c)). Mermaid Chart 의 PowerPoint 애드인(AppSource WA200006214)은 "원본이 바뀌면 다이어그램이 갱신" 된다고만 하고 결과가 이미지인지 도형인지 밝히지 않는다 ([Mermaid Chart Plugins](https://www.mermaidchart.com/plugins)). Google Slides 의 Insert > Diagram 은 스타일·단계 수 템플릿이며 **"라틴 알파벳을 쓰는 언어에서만" 삽입 가능**이라고 명시해 한국어가 제외되는 유일한 공식 제약이고 ([Google Help](https://support.google.com/docs/answer/1696521?hl=en&co=GENIE.Platform%3DDesktop)), Lucid·draw.io 애드온은 PNG 이미지를 넣고 원본 수정 뒤 "Update" 로 갱신하는 방식이다 ([Lucid Help](https://help.lucid.co/hc/en-us/articles/11175888421780-Lucid-add-ons-for-Google-Docs-Sheets-and-Slides), [draw.io FAQ](https://www.drawio.com/doc/faq/google-slides-drawio)). Beautiful.ai 는 Flow Chart Smart Slide(타원·사각·마름모 + 커넥터)를 갖고 "슬라이드이지 스크린샷이 아니다" 라고 강조하면서도 **AI 가 텍스트 프롬프트로 새 플로차트를 생성하지는 못한다**고 스스로 적어 가장 솔직한 범위 표기를 한다 ([Beautiful.ai](https://www.beautiful.ai/flowchart-maker)). Tome 은 2025-04-30 종료됐다 (2차, [Deckary](https://deckary.com/blog/tome-review)).

가장 가까운 "텍스트 → 편집 가능 객체" 경로는 Figma 쪽이다. FigJam 에 Mermaid.js 구문을 붙이면 플로차트·시스템 다이어그램·ERD 가 네이티브로 렌더되고 ([Figma Help](https://help.figma.com/hc/en-us/articles/1500005916661-Work-between-Figma-and-FigJam)), Figma MCP 의 `generate_diagram` 은 Flowchart·Gantt·State·Sequence·Architecture·ERD 를 지원한다 ([Figma Developers](https://developers.figma.com/docs/figma-mcp-server/tools-and-prompts/)); 서드파티 스킬 문서는 같은 도구가 class·journey·C4·mindmap 을 지원하지 않고 시퀀스 노트·Gantt 색상이 제거된다고 적는다 (2차, [mcpservers.org](https://mcpservers.org/agent-skills/openai/figma-generate-diagram)). 다만 FigJam 자체는 PPTX 내보내기 문서가 없고, Figma Slides 의 PPTX 내보내기는 글꼴 대체·그라데이션→단색·코드 블록/인터랙션→이미지라는 제한 목록을 두며 커넥터 보존은 명시하지 않는다 ([Figma Support](https://figma-signup.helpjuice.com/import-and-export-2/export-from-figma-slides)). PPTX 로 도형·커넥터가 객체로 넘어간다고 공식 확인되는 곳은 PowerPoint 자체, Beautiful.ai("editable PowerPoint"), Pitch(지원 요소 목록에 shapes 는 있고 선·커넥터는 없음) 정도이고 ([Pitch Help](https://help.pitch.com/en/articles/6713988-export-a-presentation-to-power-point)), Canva 는 PPTX 로 열면 "다르게 보일 수 있고" 일부 선 요소의 길이·정렬이 바뀔 수 있다고 스스로 경고한다 ([Canva Help](https://www.canva.com/en_gb/help/elements-moved-download/)).

## nexa-slide 는 상자·선·화살표를 이미 갖췄고, 빠진 것은 배치 생성뿐이다

현재 코드에는 다이어그램을 그리는 길이 두 갈래 있다. 첫째는 `diagram` 레이아웃으로, `render_mermaid.py` 가 `content/<id>.json` 의 `layout == "diagram"` 슬라이드 중 `mermaid` 필드가 있는 것을 골라 `npx -y @mermaid-js/mermaid-cli -i <mmd> -o <png> -s 2 -b white -c <cfg>` 로 PNG 를 만들고 `.mmd` 를 옆에 남기며(`studio/render_mermaid.py:33-44`, `:46-66`), 설정은 theme `base`·`Pretendard, 'Noto Sans KR', 'Malgun Gothic'` 글꼴·색 토큰 하드코딩이고 **mermaid-cli 버전 고정이 없다**(`:20-32`). 레이아웃은 PNG 의 IHDR 에서 픽셀 크기를 읽어(`studio/layouts.py:383-390`) `imgScale` 0.5 로 축소해 가운데 `b.image` 로 놓고(`:392-412`), PPTX 에서는 `add_picture`(`studio/export_pptx.py:207-212`), 편집기에서는 `<img class="rs-img">`(`studio/render.js:302-304`)다. 시작용 ERD(`starters/lecture-course/content/ch01.json:140-150`)의 PNG 에서 "주문·포함·품목" 한글 라벨이 정상 렌더된 것을 확인했으므로 호스트 글꼴이 있는 환경에서 한글은 문제가 없다. 둘째는 네이티브 요소로 그리는 레이아웃이다. `sequence`(`studio/layouts.py:291-380`)는 `actors`·`messages [from, to, y, 색, 글]`·`groups`·`loops`·`frames`(UML loop/opt/alt 프래그먼트)·`returns` 로 UML 시퀀스를 `b.arrow`+번호 원+라벨로 그리되 **y 좌표는 작성자가 px 로 직접 준다**; `flow`(`:603-640`)는 카드 선형 1열, `tree`(`studio/layouts_more.py:281-305`)는 1-N-M 수평 트리, `matrix_plot`(`:237-262`)은 2×2 사분면이다.

요소 모델과 렌더러도 준비돼 있다. `line`·`arrow` 는 `x1,y1,x2,y2`·`color`·`width`·`head`(none/end/start/both)·`dash`, `curve` 는 `points` 꺾은선이며(`docs/deck-format.md:23-24`), 편집기 `lineSvg()` 는 SVG `<line>`+삼각형 `<polygon>` 으로 머리 크기를 선 두께×5(PPT "lg")로 맞추고(`studio/render.js:307-321`), PPTX 는 `add_connector(MSO_CONNECTOR.STRAIGHT)`(`studio/export_pptx.py:215-222`)·`build_freeform`(`:225-236`)·`style_line()` 이 `a:ln` 아래 `a:headEnd/a:tailEnd type=triangle w=lg len=lg` 를 직접 넣는다(`:239-255`). 편집기에는 화살표 추가 메뉴(`studio/studio.js:1200-1203`, 기본값 `:1188`), 두 끝점 핸들 `p1/p2`(`:379`), 끝점 드래그(`:1108`), 머리 방향 토글(`:584, :656`), `x1..y2` 숫자 입력(`:620, :787`)이 있다. **없는 것은 노드-엣지 그래프 모델, 자동 배치, 요소 그룹, 선-도형 연결(붙음)** 이며(grep 에서 `group`/`connect`/`parent` 필드 없음, `docs/deck-format.md:19-30` 요소 표에 group 없음), 한 가지 더 유의할 점은 `check_parity.py` 가 code 하이라이트·인라인 강조·표 격자만 비교하고 **선·화살표 기하는 비교하지 않는다**는 것이다(`studio/check_parity.py:6`, `:46-100`). 그래서 새 도형 타입(마름모·원통·빈 삼각형 머리)을 넣는 변경은 두 렌더러를 손보되 검사망 밖이라 parity 항목 추가가 따라야 한다.

외부 엔진을 비교하면 Mermaid 가 공식 문법 색인 기준 31종(flowchart·sequence·class·state·ER·useCase·C4·block·architecture·requirement 등)으로 가장 넓고 ([Mermaid Syntax Reference](https://mermaid.js.org/intro/syntax-reference.html)), 그래프형(flowchart·state·class·ER·requirement·use case)만 dagre/ELK 를 고를 수 있으며 sequence·gantt 는 전용 배치다 ([draw.io Mermaid layout engine](https://www.drawio.com/docs/manual/mermaid/mermaid-layout-engine/)). 결정적인 변화는 **v12 부터 ELK 가 내장·기본 레이아웃**이 된 것이다 - "`layout: elk` works with no setup", 되돌리려면 `layout: dagre` ([Mermaid Layouts config](https://mermaid.js.org/config/layouts.html)). nexa-slide 가 npx 로 최신 cli 를 받는 지금 구조에서는 어느 날 기존 PNG 와 모양이 달라지므로 **버전 고정 또는 CONFIG 에 `layout: dagre` 명시**가 선행 과제다. PlantUML 은 타이밍 다이어그램까지 지원하지만 Java 와 (use case·class·component·deployment·state 에) Graphviz 가 필요하고 ([plantuml.com/graphviz-dot](https://plantuml.com/graphviz-dot), [timing-diagram](https://plantuml.com/timing-diagram)), D2 는 PPTX 를 직접 내보내지만 "PNG 를 페이지에 놓는" 방식이며 ([d2lang exports](https://d2lang.com/tour/exports)), Kroki 는 29개 엔진을 HTTP 로 묶지만 모두 이미지로 끝난다 ([kroki.io](https://kroki.io/)). "편집 가능 도형" 선례는 셋이다: mermaid-to-excalidraw 는 `mermaid.render` SVG 에서 위치·크기를, `getDiagramFromText` 에서 토폴로지를 읽되 **flowchart 만** 지원하고 나머지는 이미지 폴백이며 ([parser 문서](https://docs.excalidraw.com/docs/@excalidraw/mermaid-to-excalidraw/codebase/parser)); mmd2pptx(v0.2.4, Apache-2.0)는 Mermaid SVG 를 직접 파싱해 노드 바인딩 네이티브 커넥터를 만들되 명시 지원은 Flowchart 이고 역변환은 보류 ([GitHub](https://github.com/LJAYi/mmd2pptx)); diagram-pptx(0.1.0b3, Python≥3.10)는 python-pptx 로 flowchart·sequence·class·ER·state 를 순수 Python 네이티브 레이아웃으로 그린다 ([PyPI](https://pypi.org/project/diagram-pptx/)). 두 프로젝트 모두 0.x 베타다. python-pptx 1.0.2(설치본)는 `add_connector`·`begin_connect/end_connect`(실험적, "rectangular shapes" 에서만 안정)·`build_freeform`·`add_group_shape` 를 주지만 **화살 머리 API 가 없고 SmartArt 는 생성 불가**다 ([python-pptx shapes API](https://python-pptx.readthedocs.io/en/latest/api/shapes.html), [커넥터 분석](https://python-pptx.readthedocs.io/en/latest/dev/analysis/shp-connector.html)) - nexa-slide 가 이미 XML 직접 삽입으로 우회하는 지점이다.

이 사실들 위에서 세 접근을 비교한다. **접근 1(Mermaid 이미지 유지 + 편의 개선)** 은 현행 구조에 편집기 내 mermaid.js 라이브 미리보기·종류별 템플릿, 저장 시 서버가 PNG 재생성(`server.py` 엔드포인트 + `render_mermaid.render()` 재사용), SVG 삽입, 버전·레이아웃 고정을 더하는 것이다. 31종 전부 커버하고 parity 영향이 없으며 1주 안에 끝나지만 PPTX·편집기 모두에서 그림이다. **접근 2(Mermaid 배치 결과 → 네이티브 요소 변환)** 는 선례가 모두 flowchart 에서 멈춘 이유가 종류마다 SVG 구조와 내부 API 가 달라 파서를 따로 써야 하기 때문이며, 브라우저 경로는 글꼴 측정이 실제 값이지만 비대화형 build 에 node+puppeteer 가 필요하고, 서버 SVG 파싱 경로는 비공식 SVG 구조에 의존해 Mermaid 버전 업에 취약하다. 또 Mermaid 측정 폭이 nexa-slide 의 `text_width`(`studio/common.py:482`)와 다르면 한글이 넘칠 수 있어 변환 후 폭 보정이 필요하고, 마름모·까마귀발(ERD `o{`·`||`)·빈 삼각형(상속)은 현재 요소 타입에 없어 새 도형이 필요하다. flowchart·state 는 상, ERD·class 는 중, sequence 는 Mermaid 파싱보다 기존 `sequence` 레이아웃으로 변환(참여자·메시지만 추출)이 훨씬 싸고, swimlane·timing 은 비현실적이다. **접근 3(종류별 네이티브 구조 레이아웃)** 은 `sequence`·`flow`·`tree` 처럼 필드가 구조화된 레이아웃을 늘리는 것으로, 좌표를 (a) 격자(`nodes:[{id,text,col,row,shape}]`, `edges:[[from,to,label,style]]`)로 지정하거나 (b) Python 에 longest-path 랭크 + barycenter 정렬의 간단한 계층 배치(200~400줄)를 두거나 (c) 편집기에서 dagre(약 25KB gzip, 2차 [CALM ADR](https://calm.finos.org/calm-studio/adrs/use-elk-for-auto-layout))로 "자동 정렬" 버튼을 붙이는 세 단계로 투입할 수 있다. 격자형이면 flowchart·state·use case(액터 열+유스케이스 열)·component/deployment/package(중첩 rect)·ERD·class(3단 상자)·DFD(원·저장소 선 2개·외부 사각)·communication(격자+번호 라벨)·timing(참여자 행+계단 `curve`)까지 **과제의 12종을 전부 그릴 수 있고**, PlantUML 조차 sequence·activity·timing 을 Graphviz 없는 전용 배치로 그린다는 사실이 "종류별 전용 배치" 가 업계 표준임을 뒷받침한다 ([plantuml.com/graphviz-dot](https://plantuml.com/graphviz-dot)).

권고와 순서는 이렇다. **접근 3 격자형을 기본**으로 하되 공통 기반을 먼저 만든다 - `rect` 에 `shape: "diamond"|"cylinder"|"actor"|"store"` 변형(render.js SVG/CSS 와 export_pptx.py `MSO_SHAPE.DIAMOND`·`CAN` 두 곳 + parity 항목), 노드 경계 교점을 계산해 `arrow` 를 긋는 유틸, 요소 모델에 선택 필드 `from:{id,side}`·`to:{id,side}` 를 더해 export 에서만 `stCxn/endCxn` 을 넣는 연결(편집기는 끝점 좌표만 쓰므로 parity 영향 없음), 다이어그램 묶음을 `add_group_shape` 로 묶는 export 전용 옵션. 그 뒤 교재에 바로 쓰는 flowchart·ERD·state·DFD 4종(2~3주)을 넣고, 수요가 확인되면 class·use case·component 를 이어 간다. 접근 1 은 지금처럼 유지하되 mermaid-cli 버전 고정과 `layout: dagre` 명시, 편집기 미리보기를 더해 격자형이 없는 종류의 폴백으로 둔다. 접근 2 는 "편집기에서 Mermaid flowchart 를 네이티브 요소로 한 번 뽑는 보조 버튼" 으로 범위를 좁힐 때만 가치 대비 비용이 맞는다. 실측이 필요한 두 가지는 `begin_connect` 가 `roundRect`/`pill` 의 연결점 인덱스를 어떻게 매기는지(문서가 "보장 안 함")와, 노드 20개 내외 교재 도면에서 Python 계층 배치의 선 교차 품질이 Mermaid/ELK 에 어느 정도 미치는지다.

## 테이블 정의서는 7열·9행·머리 반복으로 3장에 담는다

정의서의 열 구성은 도구·표준을 가로질러 수렴한다. 행정안전부 『공공기관의 데이터베이스 표준화 지침』(고시 제2025-19호) 제9조는 설계 산출물 7종에 테이블정의서·컬럼정의서를 포함하고(저장소 원천 `sources/common/official-docs/korea-public-db-standardization-guide/01-guideline-articles-overview.md:71`), [별표 2] 컬럼정의서 항목은 영문테이블명·한글/영문컬럼명·컬럼설명·데이터타입·길이·**Not Null 여부("Y" = Nullable 이라는 표기 주의)**·**PK정보 `PK01, PK02…`(참여 순서)**·AK·**FK정보 `참조테이블.참조컬럼`**·제약조건(허용범위·기본값)·개인정보/암호화 여부다(`…/02-standard-dictionary-and-deliverable-items.md:138-151`). 문서 생성 도구도 같은 집합을 쓴다 - tbls 는 `Name | Type | Default | Nullable | Extra Definition | Children | Parents | Comment` ([tbls sample](https://raw.githubusercontent.com/k1LoW/tbls/main/sample/mysql/users.md)), SchemaSpy 는 `Column | Type | Size | Nulls | Auto | Default | Children | Parents | Comments` 에 PK 컬럼 음영 범례 ([SchemaSpy 생성 샘플](https://www.solgenomics.net/ftp/schemas/metadata/tables/comments.html)), DBML 은 `pk`·`not null`·`default:`·`note:`·인라인 `ref:` ([DBML docs](https://dbml.dbdiagram.io/docs/)). 즉 **보편 열 6개(컬럼명·설명·타입·NULL·기본값·PK) + 선택 열(순번·FK·UK/인덱스·도메인·개인정보)** 이 모델의 기본 필드다. 사용자 Excel 의 `PK_POS` 는 Oracle `*_CONS_COLUMNS.POSITION`, `DESCEND` 는 PK 인덱스의 `*_IND_COLUMNS.DESCEND`(ASC/DESC)를 옮긴 것으로 보이며(추정; [Oracle ALL_IND_COLUMNS](https://docs.oracle.com/en/database/oracle/oracle-database/19/refrn/ALL_IND_COLUMNS.html)), `NULLABLE` 은 Oracle·지침의 "Y = NULL 허용" 과 tbls·DBML·많은 사내 양식의 "NOT NULL 여부" 가 충돌하므로 슬라이드 열 머리를 **"NULL 허용"** 으로 명시해야 오독을 막는다.

한 장에 들어가는 양은 코드 기하에서 계산된다. 캔버스 1280×720px(pt = px×0.75, `docs/deck-format.md:12`), `table` 레이아웃의 표는 `x=64, y=180, w=1152`, 기본 `rowH=46`, 글자 16px(12pt)(`studio/layouts.py:365-372`), 바닥은 경로 y=675·각주 있으면 668 까지(`:189-192`, `:164`)이므로 세로 가용 폭은 약 **476px** - rowH 46 이면 머리 1 + **본문 9행**, 40 이면 10행, 글자 최소치 11pt 에 맞춘 36 이면 12행이다. 가로는 1152px 를 9열로 나누면 열당 100px 안팎(한글 6자)이라 설명 열이 들어가지 않으므로 **열 상한은 7개, 설명 열에는 300~400px 이상**을 준다(의견). 슬라이드 디자인 가이드도 "12~15행·여러 열이면 나누거나 단순화", "글자를 줄여 맞추지 말고 표를 재구성", "강조는 드물게" 라고 권한다 (2차, [Deckary](https://deckary.com/blog/powerpoint-table-design)). TB_BOM 23컬럼은 9행/장이면 9·9·5, 균등 분할이면 **8·8·7 세 장**이고 "(계속)" 과 "2/3" 표식이 필요하다. 현재 엔진에는 자동 분할이 없다 - `status_table` 이 9행 초과 시 경고만 찍고 그대로 그리고(`studio/layouts_extra.py:75-76`), `insight_panel` 은 `rows[:7]` 로 잘라 버린다(`studio/layouts_more.py:84`).

nexa-slide 의 표는 요소 `table` 하나로 화면(`render.js`)과 PPTX(`export_pptx.py`, `add_table` 로 만든 진짜 `a:tbl`, 스타일 "No Style, No Grid", `firstRow/bandRow` 제거, 셀 여백 L/R 14px, 아래선만 - `studio/export_pptx.py:40`, `:270-318`)가 같은 격자 규칙 `common.table_grid`(`studio/common.py:558-559`)를 쓴다. 열 폭 비율 `colW`(`:574-577`), 0.15.3 의 행별 높이 `rowH`(`:578`), 열별 글꼴 `colFont`(mono)·열별 정렬 `align`(`:585-586`), 셀 인라인 강조 `**굵게**`·`==강조==`(굵게+primary 색)·`[[토큰|글]]`(`:316-333`)이 있지만 **일반 표 본문 셀의 `fill` 은 항상 None**(`:616`, `studio/render.js:216-220`)이라 행 음영·PK 행 강조는 현재 필드로 불가능하다. 셀 배경이 있는 곳은 `plan-table` 의 `hl`(warn/ok, 본문 mono 고정 `:606`)과 `status_table`(표 요소가 아닌 `rect`+`text` 조립)뿐이다. 검사기는 표에 대해 최소 글자 크기만 보고(`studio/check_layout.py:142-150`) 셀 넘침은 보지 않으므로(`:153-176`), 긴 `COLUMN_DESC` 의 줄 수 추정과 `rowH` 늘리기는 레이아웃 빌더가 책임져야 한다.

제안하는 설계는 세 조각이다(의견, 수치는 위 기하에서 계산). 첫째, content 레이아웃 **`table_spec`** - 필드는 `table:{name, desc, owner, type}`, `columns:[{no, name, desc, type, pk(0 또는 참여 순서), nullable(Y/N, Oracle 관습으로 저장), default, fk, note}]`, `show`(기본 7열 `no·name·desc·type·pk·nullable·default`, 선택 `fk·uk·index·domain·privacy`), `colW`(예 `[50,190,330,170,60,70,282]`), `perSlide`(기본 8, 상한 9), `continued`("(계속)"), `highlight`, `callouts`, `crumb`. 요소 `table` 을 그대로 쓰므로 PPTX 에서 편집 가능한 진짜 표가 나오고, `name·type·default` 열은 이미 지원되는 `colFont` mono, `no·pk` 는 가운데 정렬이다. **장 분할은 빌더 전처리**(`build_deck.py` 가 content 한 항목 = 슬라이드 한 장을 가정하므로 `expand_slides(content)` 식으로 항목을 N 개로 펼침)에서 하되 장마다 머리 행을 반복하고 제목에 `continued`, 부제 끝에 `2/3`, 마지막 장이 2행 이하면 균등 재분배, 슬라이드 id 는 `s12a/s12b` 접미로 요청 메모 추적을 유지하며, 설명 셀 줄 수는 `text_width(desc,16)` 로 추정해 1줄 46px·2줄 66px 식 `rowH` 목록을 만들고 합이 476px 를 넘으면 `perSlide` 를 자동으로 줄인다. **강조는 엔진 변경 없이** 인라인 문법으로 - PK 셀 `==PK1==`, NOT NULL `**N**`, FK `[[lab|FK]]` - 모두 run 수준이라 PPTX 에서도 유지되고(`studio/export_pptx.py:300-303`), SchemaSpy 식 PK 행 전체 음영이 꼭 필요하면 요소 `table` 에 선택 필드 `rowFill:{행번호: 토큰}` 을 더한다 - 수정 지점은 `common.table_grid`(`:616`)·`render.js tableGrid`(`:216-220`) 두 곳이고 `export_pptx.do_table`(`:314-318`)은 이미 `c["fill"]` 을 solidFill 로 쓰므로 자동 반영되며, 0.15.3 `rowH` 와 같은 "세 곳 동일 규칙 + check_parity" 절차다. 비어 있는 코멘트는 지어내지 않고 회색 `-` 로 두며 발표자 노트에 "코멘트 없음 - 확인 질문" 을 남긴다.

둘째, **"표 + 설명"** 은 두 방식이 있다. 방식 A 는 `plan-table` 의 콜아웃 구조(표 폭을 `1152 - calloutW 380 - 24 = 748px` 로 줄이고 행 오른쪽에 연결선+둥근 상자, `studio/render.js:230-241`, `studio/export_pptx.py:320-327`)를 재사용하되 748px 에 7열은 좁으므로 콜아웃 장은 `show` 를 4~5열로 자동 축소하고, 방식 B 는 `insight_panel` 식 고정 패널(`studio/layouts_more.py:69-95`)로 핵심 컬럼 3~5개를 번호 목록으로 둔다. 교육 흐름(전체 → 핵심)에는 **본문 장은 7열 전폭, 그 뒤 "핵심 컬럼 해설" 한 장을 B(또는 A 로 5열 축소)로 두는 2단 구성**이 맞다(의견). 개요용 **`table_card`** 는 `cards` 레이아웃(`studio/layouts.py:642-665`) 변형으로 카드마다 테이블명(mono)·한글명·용도·PK 컬럼 목록(최대 5개)·컬럼 수/행 수(`tables.csv` 의 `COLUMN_COUNT`·`NUM_ROWS`)를 담아 2×3 까지 놓고, ERD(`diagram` 레이아웃의 `erDiagram`) 장 다음에 둔다.

셋째, **생성 경로 `ppt/tools/gen_table_spec.py`** 는 입력을 두 갈래로 받는다. 오프라인은 `schema/<프로파일>/snapshot/columns.csv`(머리 `TABLE_NAME,COLUMN_ID,COLUMN_NAME,DATA_TYPE,DATA_LENGTH,DATA_PRECISION,DATA_SCALE,NULLABLE,DATA_DEFAULT,COMMENTS` - `schema/SQLEDU@DEV/snapshot/columns.csv:1`)와 `tables.csv` 로, `explore_schema.py` 가 Oracle(`user_tab_columns`+`user_col_comments`, `:128-145`)·SQL Server(`sys.columns`+`MS_Description`, `:221-241`)·PostgreSQL(`pg_attribute`+`col_description`, `:356-371`) 을 같은 열로 통일해 두었다. 다만 `constraints.csv` 는 제약 단위라 **컬럼 참여 순서가 없다**(`:147-158`, `user_cons_columns` 조인 없음) - 정확한 `PK_POS` 가 필요하면 `explore_schema.py` 에 `cons_columns.csv`(constraint_name, column_name, position) 추출을 더하는 것이 가장 작은 변경이고(SQL Server 는 `sys.index_columns`/`sys.foreign_key_columns`, PG 는 `pg_constraint.conkey`), 임시로는 `ddl/TABLE/<표>.sql` 의 `PRIMARY KEY (…)` 절을 파싱해도 된다. 온라인은 `db.query_df(sql, env="BISCM@DEV")`(`schema/README.md:62`, Windows 는 PowerShell + `.venv\Scripts\python.exe`)로 저장소 원천 노트의 컬럼정의서 SQL - `'PK' || LPAD(cc.position,2,'0')`, FK `LISTAGG(rc.table_name||'.'||rcc.column_name)`, 타입 문자열 `data_type||'('||char_length||DECODE(char_used,'C',' CHAR','')||')'` (`sources/common/web-books/enterprise-da-tools-da-sharp/03-design-tools-comparison-and-no-tool-workflow.md:75-117`) - 을 돌리고 `user_ind_columns.DESCEND` 를 조인하면 사용자 Excel 의 DESCEND 열까지 재현된다. Excel 설계서 자체도 열 매핑표(`TABLE_ID→table.name, COLUMN_DESC→desc, PK_POS→pk, NULLABLE→nullable, DATA_DEFAULT→default`)만 두면 같은 모델로 수렴한다. 실행은 `python ppt/tools/gen_table_spec.py --profile SQLEDU@DEV --tables TB_BOM --deck ch06` → `build_deck ch06 --force` → `check_layout ch06` 이고, 검사기에는 `tspec.rows`(본문 9행 초과)·`tspec.cols`(7열 초과)·`tspec.descW`(설명 열 300px 미만)·`tspec.cell.spill`(`_wrap_count`, `studio/check_layout.py:46-60` 을 셀에 적용) 네 WARNING 을 더하는 것을 권한다. 교재 TOC §6.4 가 이미 "공공 산출물 7종" 과 실습 06-04 "도구 없이 컬럼정의서·Mermaid ERD 추출" 을 두고 있어(`docs/08-book-toc.md:551`, `:567`) 첫 적용 덱은 ch06 이 자연스럽다.

Microsoft 가 구조 재배치형 AI 와 문맥형 텍스트 채우기를 퇴역·취소하고 "서식·구조·브랜딩 유지" 를 전면에 세운 것은 "AI 가 구조를 멋대로 바꾸는 기능" 의 수요가 검증되지 않았다는 신호이고, Designer 의 제약은 자유 배치 요소가 많을수록 자동 레이아웃이 어렵다는 증거다 - nexa-slide 가 레이아웃(필드) 단위로 내용을 두고 "디자인은 템플릿 고정 + 요청 메모로 세션이 고침" 을 택한 것과 결이 같다. 또 다섯 도구 모두 글자 자동 축소(AutoFit)를 편집 기능으로 내세우지 않는다 - Gamma 는 카드가 늘어나고, Presentations.AI 는 추가를 막고, nexa-slide 는 검사로 알리고 세션이 고친다. 넘침 처리 방식이 도구 철학을 가른다.

nexa-slide 의 현재 위치는 `docs/editor.md`·`CHANGELOG.md`(0.3.0~0.15.3) 기준으로 **AI 세션 연계(요청 메모·영역 메모·✨ 레이아웃 고치기·✨ 다듬기·변경 탭)와 검사·PPTX 일치에서는 상용 도구와 동등하거나 앞서고**, 격차는 `editor.md` 가 스스로 적은 "다중 선택·정렬 맞추기 도구 없음, 글자 자동 맞춤 미지원, PPT 에서 고친 내용은 돌아오지 않음(단방향)" 과, AI 편집의 사전 미리보기, 덱 횡단 작업(찾기/바꾸기·다른 덱에서 장 가져오기·데이터로 여러 장), 표·차트 구조 편집(행/열 추가·병합, 차트 데이터 표), 입력 중 길이 경고에 있다. 선택 모드 빠른 칩은 글자(다듬기·더 길게·더 짧게·검증)·표(두 장으로 나누기)·검사 결과 고치기이고, 서버에는 `POST /api/newslide`, `GET /api/check/<id>`, `GET /api/history/<id>`, `POST /api/requests/<id>` 가 있다(`docs/server.md`). 이 격차를 "기능만 차용, 구성·디자인 유지" 로 걸러 우선순위를 매기면 다음과 같다(복잡도는 문서 기준 추정이며 `studio.js` 규모는 확인하지 않음).

## 결론

이번 조사가 바꾸는 인식은 "다이어그램은 외부 도구가 더 잘하니 가져오면 된다" 는 전제다. 2026년의 AI 슬라이드 제품들은 UML 을 네이티브로 그리지 않고, 왕복을 지원하는 도구조차 지오메트리를 버리며, 편집 가능 PPTX 변환기는 flowchart 에서 멈춘 0.x 베타다. 반면 nexa-slide 는 상자·선·화살표·커넥터 XML·시퀀스 레이아웃을 이미 갖고 있어 다이어그램 문제가 "렌더링" 이 아니라 "격자 좌표를 어떻게 쓰게 할 것인가" 라는 content 설계 문제로 축소된다. 같은 논리가 정의서에도 적용된다 - 엔진 변경은 선택 필드 `rowFill` 한 건으로 충분하고, 나머지는 빌더의 분할·행 높이 추정과 딕셔너리 → content 스크립트가 해결한다. 두 과제가 공유하는 유일한 엔진 비용은 "렌더러 두 벌 + parity 검사" 이며, 지금 parity 가 선 기하를 보지 않는다는 사실이 그 비용을 먼저 치러야 할 이유다.

편집 기능에서는 Microsoft 가 구조 재배치형 AI 를 퇴역시킨 흐름이 nexa-slide 의 "검사로 알리고 세션이 고친다" 철학을 사후적으로 정당화한다. 그러므로 차용의 핵심은 새 AI 기능이 아니라 세션에 보내는 요청 문구의 폭(칩)과 사람이 직접 고치는 원시 도구(다중 선택·찾기/바꾸기)이며, 이 둘은 디자인을 건드리지 않고도 요청 메모 왕복 횟수를 줄여 세션 비용을 낮춘다. 남은 불확실성은 실측 영역이다 - `begin_connect` 의 `pill` 연결점 인덱스, Python 계층 배치의 선 교차 품질, mermaid-cli v12 전환이 기존 PNG 에 주는 변화는 구현 첫 주에 작은 실험으로 확인해야 한다.
